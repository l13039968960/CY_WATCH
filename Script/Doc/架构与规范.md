# 第一部分 · cywatch-bsp-driver：BSP 驱动编写规范

> 源文件：`.claude/skills/cywatch-bsp-driver/SKILL.md`（989 行）
>
> 适用场景（原文 frontmatter 的 description，决定它何时会被自动加载）：
>
> Use when writing a NEW BSP/HAL device driver (sensor or peripheral) for this STM32F411 project, or when extending an existing one (MPU6050, MAX30102, AHT21, ST7789, LED). Encodes the project's OO-in-C architecture (struct-of-function-pointers + injected interface structs) and exact code conventions so new code matches the existing drivers. Also use it when wiring a driver for consumption by a service/task — the device-to-service adapter glue in `<DEV>/adapter/` (see §11).

## cywatch BSP 驱动编写规范

本 skill 固化本项目(STM32F411CEU6 / Keil MDK-ARM)设备驱动层的设计思路与代码规范，
以 `MPU6050` 与 `MAX30102` 两个成熟驱动为范本。**编写任何新设备驱动、或给现有驱动
增加接口时，必须严格遵循本规范**，不要自创风格。

参考实现位置:
- `MPU6050/hal_driver/{Inc,Src}/cywatch_bsp_mpu6050_driver.{h,c}`
- `MPU6050/adapter/cywatch_adapter_mpu6050.{h,c}`(设备→服务 adapter 范本, 见第 11 节)
- `MAX30102/hal_driver/{Inc,Src}/cywatch_bsp_max30102_driver.{h,c}`
- `IIC/iic_hal.{h,c}`、`GPIO/gpio_hal.{h,c}`、`SPI/spi_hal.{h,c}`(底层 OO 驱动范本)
- `Core/Src/main.c`(应用层装配范本)

---

### 1. 分层架构

```
┌─────────────────────────────────────────────────────────┐
│ 应用层  Core/Src/main.c                                 │
│   - 定义接口实例(iic/delay/interrupt...)、驱动实例        │
│   - 调 <dev>_inst() 构造 → 通过函数指针调用驱动           │
├─────────────────────────────────────────────────────────┤
│ handler 层  <DEV>/handler/{Inc,Src}/...                 │
│   - 业务/服务层(当前为空占位, 暂不实现)                    │
├─────────────────────────────────────────────────────────┤
│ adapter 层  <DEV>/adapter/cywatch_adapter_<dev>.{h,c}   │
│   - 设备驱动 -> 单个消费服务的一对一薄胶水层(无业务逻辑)│
│   - 总线实例绑成驱动接口, 暴露<服务>_bsp_*() API        │
│   - 范本 MPU6050/adapter (详见第 11 节)                 │
├─────────────────────────────────────────────────────────┤
│ hal_driver 层  <DEV>/hal_driver/{Inc,Src}/              │
│   - cywatch_bsp_<dev>_reg.h   寄存器/位域/灵敏度定义       │
│   - cywatch_bsp_<dev>_driver.h 接口结构体 + 驱动结构体 + 构造声明 │
│   - cywatch_bsp_<dev>_driver.c 静态实现 + 构造函数         │
├─────────────────────────────────────────────────────────┤
│ HAL 层  IIC/ GPIO/ SPI/ (底层 OO 驱动, 软件I2C/硬件SPI)  │
│   - <bus>_hal.h/.c 提供 <bus>_driver_t 与 <bus>_driver_inst()│
└─────────────────────────────────────────────────────────┘
```

核心思想:**用 C 语言模拟面向对象**。

- 每个设备是一个"对象"结构体 `bsp_<dev>_driver_t`, 内部全是**函数指针**;
- 依赖不直接 include 或硬编码, 而是以**接口结构体**(`iic_interface_t` 等)注入;
- 每个接口结构体带一个 `void *p_xxx_instance`(不透明实例) + 若干 `pf_*` 函数指针;
- 通过**自由构造函数** `<dev>_inst()` 完成校验 + 挂载 + 初始化 + 自检。

---

### 2. 目录与文件命名

新增设备 `<dev>`(全小写, 如 `aht21`、`st7789v`)时, 按如下结构创建:

```
<DEV>/                                 # 大写, 如 MPU6050/、AHT21_/
├── adapter/                           # 服务消费设备时的胶水层(可选, 见第 11 节)
│   ├── cywatch_adapter_<dev>.h        # 服务级 API 声明(业务方只 include 它)
│   └── cywatch_adapter_<dev>.c        # 绑定总线实例 + 一行转发驱动 pf_*
├── hal_driver/
│   ├── Inc/
│   │   ├── cywatch_bsp_<dev>_reg.h     # 寄存器地址/位域/灵敏度
│   │   └── cywatch_bsp_<dev>_driver.h  # 接口 + 驱动结构体 + 构造声明
│   └── Src/
│       └── cywatch_bsp_<dev>_driver.c  # 实现
└── handler/
    ├── Inc/cywatch_service_<dev>_handler.h
    └── Src/ec_bsp_<dev>_handler.c
```

命名规则:
- 文件前缀统一 `cywatch_bsp_`, 设备名小写: `cywatch_bsp_max30102_driver.h`;
- 类型后缀 `_t`; 指针前缀 `p_`; 函数指针前缀 `pf_`;
- 函数命名 `<dev>_<动作>` 全小写下划线, 如 `max30102_read_reg`、`mpu6050_read_accel`;
- 寄存器宏 `<DEV>_<寄存器>`, 位域宏 `<DEV>_<寄存器>_<位名>`, 大写下划线;
- adapter 例外: 文件名 `cywatch_adapter_<dev>`, 导出函数 `<consumer>_bsp_<动作>`
  (`<consumer>` = 消费该驱动的服务名), 见第 11 节。

#### 4.2 接口结构体(在各自驱动头文件中重复声明, 不抽公共头)

这些是**约定俗成的公共接口**, 每个驱动头文件都原样声明一份(与现有代码一致):

```c
/* iic接口 (void *p_iic_instance 由调用方传入, 实现多实例) */
typedef struct iic_interface
{
	void *p_iic_instance; // iic实例

	int8_t (*pf_start)(void *p_iic_instance);
	int8_t (*pf_stop)(void *p_iic_instance);
	int8_t (*pf_wait_ack)(void *p_iic_instance);
	int8_t (*pf_send_ack)(void *p_iic_instance);
	int8_t (*pf_send_not_ack)(void *p_iic_instance);
	int8_t (*pf_send_bytes)(void *p_iic_instance,
							uint8_t *pdata,
							uint8_t size);
	int8_t (*pf_receive_bytes)(void *p_iic_instance,
							   uint8_t *pdata,
							   uint8_t size);
} iic_interface_t;

#ifdef OS_SUPPORTING
/* 让出cpu接口 */
typedef struct yield_interface
{
	void (*pf_yield)(void);
} yield_interface_t;

/* OS信号量接口 (中断阻塞等待用) */
typedef struct semaphore_interface
{
	void *p_semaphore_instance;                       /* 信号量实例 */
	int8_t (*pf_wait)(void *p_semaphore_instance);    /* 阻塞等待信号量 */
	int8_t (*pf_release)(void *p_semaphore_instance); /* 释放信号量(ISR中调用) */
} semaphore_interface_t;
#endif // OS_SUPPORTING

/* 延时函数接口 */
typedef struct delay_interface
{
	void (*pf_delay)(uint32_t ms);
} delay_interface_t;

/* 时基计数器接口 (需要时间戳的设备才用) */
typedef struct timebase_interface
{
	uint32_t (*pf_get_time)(void);
} timebase_interface_t;

/* 底层中断接口 (需要外部中断的设备才用) */
typedef struct interrupt_interface
{
	void *p_interrupt_instance;                                  /* 底层中断实例 */
	void (*pf_enable_interrupt)(void *p_interrupt_instance);     /* 底层使能中断接口 */
	void (*pf_disable_interrupt)(void *p_interrupt_instance);    /* 底层失能中断接口 */
	void (*pf_interrupt_cb)(void *);                             /* 上层中断回调 */
} interrupt_interface_t;
```

> **注(设备 iic 接口形态二选一)**: 上面 `iic_interface_t` 带 `void *p_iic_instance`(调用
> 方传实例), 是 main.c 裸装配(§8)的默认形态; MPU6050 则用**去掉实例参数**的变体
> `mpu6050_iic_interface_t`, 实例由 adapter 层以无参静态转发函数绑定(见第 11 节)。
> 两种形态都允许, 写新驱动时选一种, 并在驱动头注释里写明「具体 I2C 实例由谁提供」。

#### 4.3 驱动结构体 `bsp_<dev>_driver_t`

规则:
- 成员分两段: 先**接口指针**(`p_iic_interface`、`p_delay_interface`…), 再**函数指针**(`pf_*`);
- `pf_inst` 的形参列表与 `<dev>_inst` 构造函数的形参**完全一致**;
- 每个公开能力对应一个 `pf_*`, 函数指针形参用 `struct bsp_<dev>_driver *` 自指;
- 若设备有中断, 加 `void (*pf_interrupt_cb)(struct bsp_<dev>_driver *)` 挂到下层中断。

```c
typedef struct bsp_<dev>_driver
{
	iic_interface_t *p_iic_interface;
#ifdef OS_SUPPORTING
	yield_interface_t *p_yield_interface;
#endif // OS_SUPPORTING
	delay_interface_t *p_delay_interface;

	int8_t (*pf_inst)(struct bsp_<dev>_driver *p_<dev>_instance,
					  iic_interface_t *p_iic_interface,
#ifdef OS_SUPPORTING
					  yield_interface_t *p_yield_interface,
#endif
					  delay_interface_t *p_delay_interface);

	int8_t (*pf_deinst)(struct bsp_<dev>_driver *p_<dev>_instance);
	int8_t (*pf_init)(struct bsp_<dev>_driver *p_<dev>_instance);
	int8_t (*pf_deinit)(struct bsp_<dev>_driver *p_<dev>_instance);
	int8_t (*pf_read_id)(struct bsp_<dev>_driver *p_<dev>_instance);

	/* ... 设备专属接口 pf_read_xxx / pf_change_to_xxx / pf_enable_xxx ... */

	int8_t (*pf_hibernating)(struct bsp_<dev>_driver *p_<dev>_instance);
	int8_t (*pf_wakeup)(struct bsp_<dev>_driver *p_<dev>_instance);

} bsp_<dev>_driver_t;
```

#### 4.4 构造函数声明(头文件末尾)

#### 5.2 静态底层读写(内部用, 不出现在结构体)

`write_reg` / `read_reg` / `read_multi_reg` 是每个 I2C 设备都有的私有函数, 写法固定:

```c
/******************************************************************************
 * @name    <dev>_write_reg
 * @brief   向<DEV>指定寄存器写入单字节数据
 * @param   p_<dev>_instance[in]
 * @param   reg[in] 寄存器地址
 * @param   data[in] 写入数据
 *
 * @return  0 success
 *         -1 <dev>_instance null
 *         -2 i2c write error
 *****************************************************************************/
static int8_t <dev>_write_reg(struct bsp_<dev>_driver *p_<dev>_instance,
							  uint8_t reg, uint8_t data)
{
	iic_interface_t *p_iic;
	uint8_t buf[3];

	if (NULL == p_<dev>_instance)
	{
		return -1;
	}

	p_iic = p_<dev>_instance->p_iic_interface;

	/* 组装I2C帧: [DevAddr(W), RegAddr, Data] */
	buf[0] = <DEV>_I2C_ADDR_W;
	buf[1] = reg;
	buf[2] = data;

	if (0 != p_iic->pf_start(p_iic->p_iic_instance))
	{
		return -2;
	}

	if (0 != p_iic->pf_send_bytes(p_iic->p_iic_instance, buf, 3))
	{
		p_iic->pf_stop(p_iic->p_iic_instance);
		return -2;
	}

	p_iic->pf_stop(p_iic->p_iic_instance);

	return 0;
}
```

`read_reg`(两阶段读)与 `read_multi_reg`(两阶段突发读)写法:

```c
static int8_t <dev>_read_reg(struct bsp_<dev>_driver *p_<dev>_instance,
							 uint8_t reg, uint8_t *p_data)
{
	iic_interface_t *p_iic;
	uint8_t buf[2];

	if (NULL == p_<dev>_instance) { return -1; }

	p_iic = p_<dev>_instance->p_iic_interface;

	/* Phase 1: 写寄存器地址 [DevAddr(W), RegAddr] */
	buf[0] = <DEV>_I2C_ADDR_W;
	buf[1] = reg;

	if (0 != p_iic->pf_start(p_iic->p_iic_instance)) { return -2; }
	if (0 != p_iic->pf_send_bytes(p_iic->p_iic_instance, buf, 2))
	{
		p_iic->pf_stop(p_iic->p_iic_instance);
		return -2;
	}

	/* Phase 2: 重复起始 + 读 [DevAddr(R)] → 接收数据 */
	buf[0] = <DEV>_I2C_ADDR_R;

	if (0 != p_iic->pf_start(p_iic->p_iic_instance))
	{ p_iic->pf_stop(p_iic->p_iic_instance); return -2; }
	if (0 != p_iic->pf_send_bytes(p_iic->p_iic_instance, buf, 1))
	{ p_iic->pf_stop(p_iic->p_iic_instance); return -2; }
	if (0 != p_iic->pf_receive_bytes(p_iic->p_iic_instance, p_data, 1))
	{ p_iic->pf_stop(p_iic->p_iic_instance); return -2; }

	p_iic->pf_stop(p_iic->p_iic_instance);

	return 0;
}
```

`read_multi_reg` 与 `read_reg` 唯一区别: Phase 2 调
`pf_receive_bytes(p_iic->p_iic_instance, p_data, size)`, 用于连续地址递增读取。

#### 5.3 构造函数 `<dev>_inst`(核心)

**构造流程固定: 逐接口校验 → 挂载函数指针 → 调用 init → read_id 自检。**

```c
/******************************************************************************
 * @name    <dev>_inst
 * @brief   instancetiate the <DEV> instance
 * @param   p_<dev>_instance[in]
 * @param   p_iic_interface[in]
 * @param   p_yield_interface[in]
 * @param   p_delay_interface[in]
 *
 * @return  0 success
 *         -1 <dev>_instance null
 *         -2 iic_interface null
 *         -3 rtos_yield null
 *         -4 delay null
 *         -5 <dev> ADDR error
 *****************************************************************************/
int8_t <dev>_inst(bsp_<dev>_driver_t *p_<dev>_instance,
				  iic_interface_t *p_iic_interface,
				  yield_interface_t *p_yield_interface,
				  delay_interface_t *p_delay_interface)
{
	if (NULL == p_<dev>_instance)
	{
		return -1;
	}

	/* 逐接口校验: 先判结构体指针, 再判内部函数指针 */
	if (NULL == p_iic_interface)
	{
		return -2;
	}
	else
	{
		if (NULL == p_iic_interface->pf_receive_bytes ||
			NULL == p_iic_interface->pf_send_ack ||
			NULL == p_iic_interface->pf_send_bytes ||
			NULL == p_iic_interface->pf_send_not_ack ||
			NULL == p_iic_interface->pf_start ||
			NULL == p_iic_interface->pf_stop ||
			NULL == p_iic_interface->pf_wait_ack ||
			NULL == p_iic_interface->p_iic_instance)
		{
			return -2;
		}
	}

	if (NULL == p_yield_interface)
	{
		return -3;
	}
	else
	{
		if (NULL == p_yield_interface->pf_yield) { return -3; }
	}

	if (NULL == p_delay_interface)
	{
		return -4;
	}
	else
	{
		if (NULL == p_delay_interface->pf_delay) { return -4; }
	}

	/* 保存接口指针 */
	p_<dev>_instance->p_iic_interface    = p_iic_interface;
	p_<dev>_instance->p_yield_interface  = p_yield_interface;
	p_<dev>_instance->p_delay_interface  = p_delay_interface;

	/* 挂载函数指针 */
	p_<dev>_instance->pf_inst     = <dev>_inst;
	p_<dev>_instance->pf_deinst   = <dev>_deinst;
	p_<dev>_instance->pf_init     = <dev>_init;
	p_<dev>_instance->pf_deinit   = <dev>_deinit;
	p_<dev>_instance->pf_read_id  = <dev>_read_id;
	p_<dev>_instance->pf_hibernating = <dev>_hibernating;
	p_<dev>_instance->pf_wakeup   = <dev>_wakeup;
	/* ... 其余 pf_xxx = <dev>_xxx ... */

	/* 初始化 + 自检 */
	p_<dev>_instance->pf_init(p_<dev>_instance);

	if (p_<dev>_instance->pf_read_id(p_<dev>_instance) != <DEV>_ID)
	{
		p_<dev>_instance->pf_deinst(p_<dev>_instance);
		return -5;
	}
	else
	{
		return 0;
	}
}
```

#### 5.4 析构函数 `<dev>_deinst`

```c
static int8_t <dev>_deinst(bsp_<dev>_driver_t *p_<dev>_instance)
{
	if (NULL == p_<dev>_instance) { return -1; }

	p_<dev>_instance->pf_deinit(p_<dev>_instance);

	p_<dev>_instance->p_iic_interface   = NULL;
	p_<dev>_instance->p_yield_interface = NULL;
	p_<dev>_instance->p_delay_interface = NULL;
	p_<dev>_instance->pf_inst    = NULL;
	p_<dev>_instance->pf_deinst  = NULL;
	p_<dev>_instance->pf_init    = NULL;
	p_<dev>_instance->pf_deinit  = NULL;
	p_<dev>_instance->pf_read_id = NULL;
	/* ... 全部函数指针清 NULL ... */

	return 0;
}
```

#### 5.5 init(编号步骤 + 每步独立错误码)

```c
static int8_t <dev>_init(bsp_<dev>_driver_t *p_<dev>_instance)
{
	int8_t ret = 0;

	if (NULL == p_<dev>_instance) { return -1; }

	/* 1. 软件复位设备 */
	ret = <dev>_write_reg(p_<dev>_instance, <DEV>_<CTRL_REG>, <DEV>_RESET);
	if (0 != ret) { return -2; }

	/* 等待复位完成 */
	p_<dev>_instance->p_delay_interface->pf_delay(<DEV>_STARTUP_DELAY_MS);

	/* 2. 配置 ... */
	ret = <dev>_write_reg(p_<dev>_instance, <DEV>_<CFG_REG>, <DEV>_DEFAULT_XXX);
	if (0 != ret) { return -3; }

	/* ... */

	return 0;
}
```

规范要点:
- 每个初始化步骤一个编号注释 `/* N. 说明 */`;
- 每步失败返回一个**从 -2 递增**的错误码, 并与函数 `@return` 文档一一对应;
- 复位/唤醒/时钟稳定后用 `pf_delay(<DEV>_STARTUP_DELAY_MS)` 等待。

### 6. 寄存器头文件 `cywatch_bsp_<dev>_reg.h`

结构固定: I2C 地址 → 器件 ID → 寄存器地址(按功能分组) → 位域掩码与取值 → 灵敏度/采样常量。

```c
/* <DEV> I2C地址 */
#define <DEV>_I2C_ADDR        0x68

/* ID */
#define <DEV>_ID              0x68

/*============================ 寄存器地址 ============================*/

/*---- 配置寄存器 ----*/
#define <DEV>_<REG>           0x1A    /* 说明 */

/*============================ 位域掩码与取值 ============================*/

/*---- <REG> (0x1A) ----*/
#define <DEV>_<REG>_<FIELD>_MASK  0x07    /* bit2-0: 说明 */
#define <DEV>_<REG>_<FIELD>_A     0x00    /* 取值A */
#define <DEV>_<REG>_<FIELD>_B     0x01    /* 取值B */

/*============================ 传感器灵敏度 ============================*/
#define <DEV>_SENS_<量程>     16384.0f
```

要点: 每个宏后带 `/* bitN: 说明 */` 或 `/* 说明 */` 中文注释;
位域用 `_MASK` 后缀, 枚举取值用 `_A`/`_B` 语义名; 分组注释用 `/*---- ... ----*/`。

### 7. 代码规范清单(逐条遵守)

1. **缩进**: 1 tab = 4 空格(`@note 1 tab == 4 spaces!`)。
2. **返回类型**: 状态返回 `int8_t`; 数据长度/计数用 `uint8_t`; 采样原始值用 `uint32_t`; 物理量用 `float`。
3. **返回码**: `0` = 成功; 负数 = 错误。错误码语义固定:
   - `-1` 一律是 `xxx_instance null`;
   - 其余从 `-2` 起按函数内出现顺序递增, 并写进 `@return`。
4. **NULL 判断**: `if (NULL == p_xxx)`(常量在左)。
5. **返回值判断**: `if (0 != ret)`。
6. **函数注释**: 每个函数前必须有 `@name/@brief/@param/@return/@note` 注释块, 用 `*****` 分隔。
7. **参数方向标注**: 输入 `[in]`, 输出 `[out]`。
8. **注释语言**: 中文说明; 标识符/代码保持英文。
9. **命名**: `<dev>_<动作>`; 指针 `p_`; 函数指针 `pf_`; 结构体 `_t`。
10. **接口注入**: 设备驱动**不直接依赖** HAL 具体实现, 只依赖接口结构体; 应用层负责实例化并传入。
11. **中断纪律**(MAX30102 教训): 中断回调(`pf_interrupt_cb`)内**只置标志**, 不做 I2C/printf/耗时操作; 实际读放在主循环。I2C 总线不可重入, 禁止在 ISR 里并发访问。
12. **寄存器读写**: 统一走 `write_reg` / `read_reg` / `read_multi_reg` 三个静态私有函数, 不散落拼帧代码。
13. **服务消费设备**: 服务/任务**不直接** include 驱动头或触碰总线实例; 需要时在
    `<DEV>/adapter/` 加一层薄 adapter, 服务只调用其 `<consumer>_bsp_*()` API(第 11 节)。

### 9. HAL 底层驱动规范 (IIC/GPIO/SPI/EXTI/UART)

HAL 层是位于 `hal_driver` 之下的**最底层硬件操作驱动**, 与 BSP 设备驱动同样采用
OO-in-C 结构, 但职责更单一: 只封装一种外设/总线的裸操作, 不含业务逻辑。

参考实现:
- `IIC/iic_hal.{h,c}` —— 软件(位模拟)I2C
- `GPIO/gpio_hal.{h,c}` —— GPIO 引脚读写
- `SPI/spi_hal.{h,c}` —— 硬件 SPI(阻塞 + DMA)
- `EXTI/exti_hal.{h,c}` —— 外部中断(NVIC + 线号分发表)
- `UART/uart_hal.{h,c}` —— 硬件 UART(环形缓冲 + DMA 收发 + IDLE 接收)

**HAL 层同样遵守依赖注入**: 与 BSP 层一致, 延时**不直接调用系统函数**,
以接口结构体注入。5 个 HAL 驱动(`IIC`/`GPIO`/`SPI`/`EXTI`/`UART`)的构造函数统一接收
一个 `<bus>_delay_interface_t`(仅含 `pf_delay_us`), 由调用方绑定 `delay_us`;
驱动结构体持有 `p_delay_interface` 成员, `inst` 校验、`deinst` 清空。

```c
/* 延时接口 (由调用方注入, 各HAL驱动一致) */
typedef struct
{
	void (*pf_delay_us)(uint32_t us); /* 微秒延时 */
} <bus>_delay_interface_t;
```

SPI 另外还有 `spi_timebase_interface_t`(时基)用于 DMA 等待超时;
UART 为环形缓冲+IDLE+DMA 模式, 收发由中断回调驱动, **不注入时基接口**。
阻塞收发用 HAL 超时, 均不直调 `delay_*`。

#### 9.1 目录与文件命名

与 BSP 设备不同, HAL 层放在**顶层目录**(`IIC/`、`GPIO/`、`SPI/`、`EXTI/`、`UART/`), 不在 `<DEV>/` 下;
文件名 `<bus>_hal.{h,c}`(`<bus>` = `iic`/`gpio`/`spi`/`exti`/`uart`), 无 `cywatch_bsp_` 前缀。
其余命名规则同 BSP 层: 类型 `_t`、指针 `p_`、函数指针 `pf_`、构造函数 `<bus>_driver_inst()`。

#### 9.2 配置结构体 `<bus>_cfg_t`

封装该外设的硬件资源, 指针成员 `p_` 前缀、值成员小写:

```c
/* SPI硬件配置 */
typedef struct
{
	SPI_TypeDef *p_spi_base;      /* SPI外设基地址(如SPI1) */
	SPI_InitTypeDef init;         /* SPI初始化参数(模式/极性/相位等) */
	DMA_HandleTypeDef *p_hdma_tx; /* TX DMA句柄(可为NULL) */
	uint32_t tx_timeout_tick;     /* 裸机DMA发送超时计数(ms) */
} spi_cfg_t;

/* I2C总线硬件配置 */
typedef struct
{
	GPIO_TypeDef *p_sda_port; /* SDA引脚端口 */
	GPIO_TypeDef *p_scl_port; /* SCL引脚端口 */
	uint16_t sda_pin;         /* SDA引脚号 */
	uint16_t scl_pin;         /* SCL引脚号 */
} iic_bus_t;
```

#### 9.3 驱动结构体 `<bus>_driver_t`

成员分三段: `cfg` 配置 → `pf_inst`/`pf_deinst`(构造/析构, 用 `struct <bus>_driver *`
自指) → 底层操作函数指针(用 `void *`, 便于注入上层接口结构体):

```c
typedef struct spi_driver
{
	/* 第一个成员: 内嵌HAL句柄(按值), 供DMA完成回调 container_of 反查实例 */
	SPI_HandleTypeDef hspi;
	spi_cfg_t cfg; /* 硬件配置 */

#ifdef OS_SUPPORTING
	spi_semaphore_interface_t *p_semaphore_interface; /* OS信号量 */
#endif
	spi_timebase_interface_t *p_timebase_interface;   /* 裸机时基计数器 */
	volatile uint8_t tx_complete; /* 每实例完成标志(ISR置位) */
	uint32_t tx_start_tick;       /* 发送启动时刻(裸机超时计数) */

	int8_t (*pf_inst)(struct spi_driver *p_spi_instance, spi_cfg_t *p_cfg);
	int8_t (*pf_deinst)(struct spi_driver *p_spi_instance);

	int8_t (*pf_transmit)(void *p_spi_instance, uint8_t *pdata, uint32_t size);
	/* ... 其余 pf_receive / pf_transmit_dma ... */
} spi_driver_t;
```

要点:
- `pf_inst` 形参与 `<bus>_driver_inst()` 构造函数形参**完全一致**;
- 操作函数指针第一个参数一律 `void *`, 内部 `(spi_driver_t *)p_ctx` 强转,
  这样可直接赋值给上层 `xxx_interface_t` 里的 `pf_*` 回调;
- **多实例**: 把 HAL 句柄(如 `SPI_HandleTypeDef`)**按值内嵌为第一个成员**, 在 HAL
  完成回调里 `(spi_driver_t *)hspi` 强转即可反查实例, 状态存实例成员而非文件级
  `static` 变量(见 §9.5)。

#### 9.4 构造函数 `<bus>_driver_inst`

流程固定: **逐项校验 → 加载 cfg → HAL 初始化 → 挂载函数指针**:

```c
int8_t spi_driver_inst(spi_driver_t *p_spi_instance, spi_cfg_t *p_cfg,
#ifdef OS_SUPPORTING
					   spi_semaphore_interface_t *p_semaphore_interface,
#endif
					   spi_timebase_interface_t *p_timebase_interface)
{
	if (NULL == p_spi_instance)      { return -1; }
	if (NULL == p_cfg)               { return -2; }
	if (NULL == p_cfg->p_spi_base)   { return -3; }

	p_spi_instance->cfg = *p_cfg;

	/* 构建内嵌句柄(首个成员, 供DMA回调反查实例)并初始化 */
	p_spi_instance->hspi.Instance = p_cfg->p_spi_base;
	p_spi_instance->hspi.Init     = p_cfg->init;
	p_spi_instance->hspi.hdmatx   = p_cfg->p_hdma_tx;
	if (NULL != p_cfg->p_hdma_tx) { p_cfg->p_hdma_tx->Parent = &p_spi_instance->hspi; }
	if (HAL_OK != HAL_SPI_Init(&p_spi_instance->hspi)) { return -4; }

	p_spi_instance->pf_inst     = spi_driver_inst;
	p_spi_instance->pf_deinst   = spi_deinst;
	p_spi_instance->pf_transmit = spi_transmit;
	/* ... */

	return 0;
}
```

返回码同 BSP 层: `0` 成功, `-1` instance null, `-2` 起按校验顺序递增。
内嵌句柄需 `HAL_xxx_Init(&instance->hspi)`, DMA 句柄 `Parent` 回指 `&instance->hspi`。

#### 9.5 中断等待: OS信号量 / 裸机计数器 (SPI DMA / BSP INT)

底层 HAL 外设中断(如 SPI DMA 完成)与 BSP 芯片 INT 引脚中断的**阻塞等待**统一遵循
同一模式, 两种环境二选一:

- **OS 环境**: 中断服务函数里**释放信号量**(`pf_release`), 等待方调用**信号量等待**
  (`pf_wait`) 阻塞等待;
- **裸机环境**: 用**计数器**(时基 `pf_get_time`)判断超时, 轮询完成标志直到完成或超时。

**多实例**: 完成回调是全局弱函数, 通过**内嵌句柄(首个成员) + 强转**反查实例——
`HAL_SPI_TxCpltCallback` 收到的 `hspi` 即 `&p_spi->hspi`, 偏移为 0, 直接 `(spi_driver_t *)hspi`
即得实例, 每实例状态(`tx_complete`)互不干扰:

```c
/* ISR: container_of 反查实例; OS释放信号量 / 裸机置完成标志 */
void HAL_SPI_TxCpltCallback(SPI_HandleTypeDef *hspi)
{
	spi_driver_t *p_spi = (spi_driver_t *)hspi; /* hspi 为首个成员, 偏移0 */
	p_spi->tx_complete = 1;
#ifdef OS_SUPPORTING
	if (NULL != p_spi->p_semaphore_interface && NULL != p_spi->p_semaphore_interface->pf_release)
		p_spi->p_semaphore_interface->pf_release(p_spi->p_semaphore_interface->p_semaphore_instance);
#endif
}

/* DMA发送: 启动+等待合并, 阻塞至完成/超时 */
static int8_t spi_transmit_dma(void *p_ctx, uint8_t *pdata, uint32_t size)
{
	spi_driver_t *p_spi = (spi_driver_t *)p_ctx;
	/* ... 校验: -1 instance / -2 hdmatx / -3 等待接口 ... */
	p_spi->tx_complete = 0;
#ifdef OS_SUPPORTING
	if (HAL_OK != HAL_SPI_Transmit_DMA(&p_spi->hspi, pdata, size)) { return -4; }
	if (0 != p_spi->p_semaphore_interface->pf_wait(
			p_spi->p_semaphore_interface->p_semaphore_instance)) { return -5; }
#else
	p_spi->tx_start_tick = p_spi->p_timebase_interface->pf_get_time();
	if (HAL_OK != HAL_SPI_Transmit_DMA(&p_spi->hspi, pdata, size)) { return -4; }
	while (0 == p_spi->tx_complete)
	{
		if ((p_spi->p_timebase_interface->pf_get_time() - p_spi->tx_start_tick)
			>= p_spi->cfg.tx_timeout_tick) { return -5; } /* 超时 */
	}
#endif
	return 0;
}
```

要点:
- `OS_SUPPORTING` 宏是开关: 定义时编译信号量分支, 未定义时编译计数器分支;
- 裸机下信号量为占位实现(无 RTOS 时 `pf_wait`/`pf_release` 空返回), 集成 RTOS 时替换为真实 API;
- 驱动需注入 `semaphore_interface`(OS) 与 `timebase_interface`(裸机计数器);
- 完成标志与启动时刻存**实例成员**, 不要用文件级 `static`(否则只能单实例)。

BSP 芯片 INT 引脚中断同理, 但由 EXTI → 驱动 `pf_interrupt_cb` → 上层 `pf_interrupt_cb`
调度(参考 MAX30102), 等待同样走信号量/计数器: 驱动提供 `pf_wait_interrupt`,
中断回调 `max30102_irq_cb` 内 OS 释放信号量 / 裸机置 `irq_flag`。

与 BSP 层中断纪律一致: 中断内只置标志/释放信号量, 不 SPI/I2C/printf; 软件 I2C 不可重入, 禁止在 ISR 访问。

#### 9.6 UART 环形缓冲 + DMA + IDLE 模式 (uart_hal)

`uart_hal.{h,c}` 实现「DMA 收发 + 环形缓冲」, 接收另加 IDLE 中断做不定长接收;
**在接收/发送完成回调(中断上下文)里把 DMA 缓冲数据搬进环形缓冲, 数据处理在主循环**。
**环形缓冲由 HAL 层持有维护**(`UART_TX_RING_SIZE`/`UART_RX_RING_SIZE`/`UART_RX_DMA_BUF_SIZE`
宏控制大小, 内嵌于 `uart_driver_t` 成员, 实例须为全局变量), `uart_cfg_t` 不含缓冲字段;
**不提供阻塞收发接口**(`pf_transmit`/`pf_receive` 不存在), 上层仅通过 `pf_*` 访问数据。

- 接收: `HAL_UARTEx_ReceiveToIdle_DMA`(RX DMA 须 **CIRCULAR**)
  → `HAL_UARTEx_RxEventCallback(huart, Size)` 触发(IDLE / 半传输 / 写满三种事件),
  用 `n = (Size + buf_size - rx_dma_pos) % buf_size` 计算新数据并搬进 RX 环;
- 发送: 主循环 `pf_tx_send()` 写 TX 环 → 空闲时 `HAL_UART_Transmit_DMA`(TX DMA 须 **NORMAL**)
  发一段连续数据 → `HAL_UART_TxCpltCallback` 推进读索引并续传下一段;
- 事件回调里搬数据仅内存拷贝, 不做 I2C/printf/耗时操作; 主循环 `pf_rx_get_count()/pf_rx_read()/pf_tx_send()` 处理。

**硬性要求(踩坑记录)**:
- **RX DMA 流中断优先级必须高于 USART 中断优先级**: F4 HAL 循环 DMA 下 HT 半传输事件
  固定传 `Size = 长度/2`, 若 IDLE 先于 HT 处理, `Size` 会过期导致搬运错位;
- DMA 句柄 `Parent` 回指内嵌 `huart`(首个成员), 回调 `(uart_driver_t *)huart` 强转反查实例;
- 环形缓冲用「空一格」判满(容量 = size-1), RX 环建议 ≥ 2× DMA 直通缓冲, 防主循环响应慢时丢数据;
- 主循环 `pf_tx_send` 先写环再查 busy 才发 DMA, ISR 先推进读索引再续传, 单生产者-单消费者无需加锁;
- 应用 ISR 接线: `USARTx_IRQHandler`→`pf_irq_handler`(HAL_UART_IRQHandler), DMA 流 IRQ→`pf_dma_*_irq_handler`。

### 10. 新增一个驱动的完整步骤

1. 建目录 `<DEV>/hal_driver/{Inc,Src}` 与 `<DEV>/handler/{Inc,Src}`。
2. 写 `cywatch_bsp_<dev>_reg.h`: I2C 地址、ID、寄存器、位域、灵敏度(第 6 节)。
3. 写 `cywatch_bsp_<dev>_driver.h`: 文件头 + 接口结构体(第 4 节) + 驱动结构体 + 构造声明。
4. 写 `cywatch_bsp_<dev>_driver.c`: 文件头 + 默认配置宏 + 前向声明 + 三个静态读写函数 +
   `init`/`deinit`/`read_id` + 设备专属函数 + `inst`/`deinst`(第 5 节)。
5. 装配(二选一): **裸机单点调用** → 在 `main.c` 定义接口/总线实例, 调 `<dev>_inst()`
   构造后自测(第 8 节); **被服务/任务消费** → 写 `<DEV>/adapter/` adapter, 服务只
   include 它并调 `<consumer>_bsp_*()`(第 11 节)。
6. 按第 7 节清单逐条自查命名、注释、返回码、缩进。

编写时**始终以 `MPU6050`/`MAX30102` 为参照**, 不确定的写法先打开对应文件对照,
保证新代码与既有驱动在结构、命名、注释风格上完全一致。

### 11. 服务消费设备时的 adapter 层设计模式

当某**设备驱动**要交给一个**服务/任务**使用(而非由 main.c 裸装配)时, 在服务与驱动
之间加一层薄 **adapter**(服务级装配)。范本: `MPU6050/adapter/cywatch_adapter_mpu6050.{c,h}`,
消费方为姿态解算服务 `service/AttitudeCalculation/cywatch_service_AttitudeCalculation.c`。

adapter 只解决「驱动 → 服务」这段接线; 服务侧自身的写法(任务/状态机/消息队列/纯算法
模块拆分)见 `cywatch-service` skill。

#### 11.1 为什么需要这层(两条装配路线)

| 场景 | 做法 | 位置 |
|---|---|---|
| 裸机/单点调用驱动 | main.c 定义接口实例 + 总线实例, 直调 `<dev>_inst()` | 第 8 节 |
| 服务/任务消费驱动 | 服务**只 include adapter**, 调 `<consumer>_bsp_*()` API | 本节 |

adapter 替服务回答三个「归谁」的问题:

- **谁持有设备实例**: adapter 文件级 `static bsp_<dev>_driver_t <dev>_instance;`;
- **谁绑定具体总线**: adapter `extern` 应用层定义的 `iic_driver_t iic_instance`
  (main.c 里创建, 不自己再建总线), 把它封装成驱动接口;
- **服务看到什么**: 一组与驱动能力一一对应、只返回 `int8_t` 的 `<consumer>_bsp_*()`,
  不出现结构体/寄存器/总线/RTOS 概念。

> 关键前提: MPU6050 驱动接口**故意去掉实例参数**(驱动头注释「具体I2C实例由适配器层
> 绑定转发」), 因此它**不能**像 §8 那样由 main.c 注入实例, 只能靠 adapter 用无参静态
> 转发函数把 `pf_*` 接到具体总线(与 §4.2 注呼应)。

#### 11.2 目录、命名与工程接线

```
<DEV>/adapter/
├── cywatch_adapter_<dev>.h    # 服务级 API 声明(业务方只 include 它)
└── cywatch_adapter_<dev>.c    # 绑定总线实例 + 一行转发驱动 pf_*
```

- 文件前缀 `cywatch_adapter_<dev>`; 导出函数前缀 `<consumer>_bsp_<动作>`, 全部返回
  `int8_t`(错误码语义同 §7: `0` 成功, `-1` 起为负);
- Keil: `<DEV>/adapter` 单独成组 + 加 IncludePath(照 `MDK-ARM/add_attitude_service_groups.py`);
- 消费服务相对 include: `#include "../../MPU6050/adapter/cywatch_adapter_mpu6050.h"`。

> **已知命名漂移(遵循 CLAUDE.md「不获准不改」)**: 文件以**设备**命名
> (`cywatch_adapter_mpu6050.*`), 函数以**消费服务**命名(`attitudecalculation_bsp_*`),
> 即一个 adapter = 「一个设备 × 一个服务」。

#### 11.3 头文件骨架 `cywatch_adapter_<dev>.h`

```c
#ifndef __CYWATCH_ADAPTER_<DEV>_H__
#define __CYWATCH_ADAPTER_<DEV>_H__

#include <stdint.h>

int8_t <consumer>_bsp_inst(void);                  /* 挂接口实例 + 调 <dev>_inst(含 read_id 自检) */
int8_t <consumer>_bsp_deinst(void);
int8_t <consumer>_bsp_read_id(void);
/* ... 与驱动公开能力一一对应: 薄转发, 不加业务参数/逻辑 ... */

#endif
```

#### 11.4 源文件骨架 `cywatch_adapter_<dev>.c`

```c
#include "cywatch_adapter_<dev>.h"
#include "../hal_driver/Inc/cywatch_bsp_<dev>_driver.h"  /* 驱动接口 + 构造函数 */
#include "../../IIC/iic_hal.h"                           /* iic_driver_t 定义 */
#include "cmsis_os2.h"                                   /* osDelay(RTOS 延时) */

static bsp_<dev>_driver_t <dev>_instance;        /* 1. 持有设备实例 */
extern iic_driver_t iic_instance;                /* 2. 引用 main.c 定义的总线实例 */

static <dev>_iic_interface_t   <dev>_iic_interface_instance;
static <dev>_yield_interface_t <dev>_yield_instance;
static <dev>_delay_interface_t <dev>_delay_instance;

/* 3. OS 适配: osDelay 返回 osStatus_t, 驱动要求 void(*)(uint32_t), 包一层丢弃返回值.
      @note 依赖调度器运行 —— <consumer>_bsp_inst() 内含延时, 必须在 osKernelStart()
      之后的任务上下文调用 */
static void <dev>_delay_cb(uint32_t ms)
{
    (void)osDelay(ms);
}

static void yield(void)
{
}

/* 4. 驱动接口「无实例参数」→ 无参静态转发, 接到具体总线实例 iic_instance */
static int8_t iic_start(void)
{
    return iic_instance.pf_start(&iic_instance);
}
/* ... iic_stop / wait_ack / send_ack / send_not_ack / send_bytes / receive_bytes
     同款一行转发, 与驱动接口结构体里的 pf_* 一一对应 ... */

/* 5. 构造: 逐项填接口结构体 → 调 <dev>_inst(), 原样返回错误码(内含 read_id 自检) */
int8_t <consumer>_bsp_inst(void)
{
    <dev>_iic_interface_instance.pf_start = iic_start;
    <dev>_iic_interface_instance.pf_stop  = iic_stop;
    /* ... 逐项挂 pf_* ... */
    <dev>_yield_instance.pf_yield = yield;
    <dev>_delay_instance.pf_delay = <dev>_delay_cb;

    return <dev>_inst(&<dev>_instance,
                      &<dev>_iic_interface_instance,
                      &<dev>_yield_instance,
                      &<dev>_delay_instance);
}

/* 6. 其余 <consumer>_bsp_*(): 一行转发驱动 pf_*, 只做参数透传 */
int8_t <consumer>_bsp_read_accel(float *p_x, float *p_y, float *p_z)
{
    return <dev>_instance.pf_read_accel(&<dev>_instance, p_x, p_y, p_z);
}
```

#### 11.5 消费方(服务)怎么用

- 服务模块只 include `cywatch_adapter_<dev>.h`, 不再 include 驱动头/总线头;
- 在**任务入口**做 `bsp_inst()`(不是 init 里), 失败重试交给服务层状态机:

```c
/* 任务内, osKernelStart() 之后; 上电瞬间传感器未就绪/总线未稳定则周期重试 */
while (0 != <consumer>_bsp_inst())
{
    osDelay(500);
}
```

#### 11.6 硬性约束(踩坑记录)

1. `*_bsp_inst()` 内含 `osDelay`(驱动复位/时钟稳定等待)→ 只能放**调度器启动后的任务
   上下文**, 不能放 `osKernelStart()` 之前的 main 初始化里;
2. 软件 I2C 全工程单总线、**不可重入** → adapter 只转发不加锁, 不跨任务并发访问, 禁止
   ISR 内调用(§7 中断纪律同源);
3. 健康恢复(读 `WHO_AM_I` 看门狗、连续失败计数进 EVT_ERROR 等)归**服务层状态机**,
   adapter 保持「调一次返回一个码」, 内部不写死循环;
4. 单位换算(LSB → g、°/s)在**驱动层**完成(`raw / <DEV>_SENS_*`), adapter 只透传 float,
   不做量纲变换;
5. 一个 adapter = 一个「设备 × 服务」组合; 未来同设备被多服务消费时, 在「每服务一个
   adapter」与「导出函数改回设备语义 `<dev>_bsp_*`、服务内再包业务层」之间取舍(见 §11.2
   命名漂移注)。

### 1. 分层定位与职责边界

```
┌ 应用层 main.c ───────────────────────────────────────────────────┐
│  外设/时钟/延时/软件I2C → osKernelInitialize → enable 页面       │
│  → 各 service_<svc>_init() + service_appcore_init()              │
│  → osKernelStart()                                               │
├ service 层 service/ ─────────────────────────────────────────────┤
│  <Svc>/cywatch_service_<Svc>.{c,h}   生产者服务: 任务+状态机      │
│    ├ 控制队列 osMessageQueueId_t(收 EVT_SLEEP/EVT_WAKEUP 等)     │
│    ├ 经 <DEV>/adapter 采样设备, 喂 ServiceFunction 纯算法         │
│    └ 产出的"最新帧"经 x_port_easyapp_event_send() 发布为事件      │
│  app_core/cywatch_service_appcore.{c,h}  分发器: 循环 easyapp_core_run() │
├ 事件框架 APP/EasyAPP/(框架代码, 通常不改, 见 §4) ────────────────┤
│  inc/easyapp_page.h  EVT 全局事件枚举 + 页表/注册宏               │
│  port/easyapp_port.{c,h}  OSSUPPORT + x_port_easyapp_event_send   │
│  src/easyapp_{core,event,page}.c  扫描/静态ring/页锚点            │
├ 页面层 APP/APPPAGE/<Page>/cywatch_app_*.{c,h} ────────────────────┤
│  注册"本页关心的事件", handler 在 app_core 任务上下文被调          │
├ adapter 层 <DEV>/adapter/(见 cywatch-bsp-driver §11)              │
├ hal_driver 层 <DEV>/hal_driver/ ...                              │
└ HAL 层 IIC/GPIO/SPI/ ...                                          │
```

职责边界(谁不能越界):

- **生产者服务不知道"谁在消费"**: 只 `x_port_easyapp_event_send(id, flags, data)`, 不发
  到具体页面、不含 UI/页面概念。消费方(页面)通过注册关系自动收到;
- **页面不做采集/计算**: 只按 `event->event_id` 分支消费, 需要数据时把
  `event_data` 转成生产者声明的数据类型读走;
- **服务壳 = 编排, 不含算法**: "何时读、失败怎么重试、何时发什么事件"归它, "怎么算"
  外包给 ServiceFunction 纯算法模块;
- **纯算法模块 = 只会算, 不认识世界**(见 §9): 不 include 驱动/adapter/EasyAPP/cmsis,
  不做 I/O;
- **服务不得直接 include 驱动头/总线**: 需要设备就经 adapter 的 `<consumer>_bsp_*()`;
- **服务之间不得直接通信**: 不 include 对方的服务头、不调对方的 `service_<svc>_*()`、
  不读对方的静态量。需要多服务协作时由 **APP 层(页面)** 编排 —— 见下面 R3 与 §13.5;
- **软件 I2C 不可重入 + 临界区纪律**: 见 §6/§7。事件发送在任务上下文、临界区内做,
  中断里只置标志, 不直接发事件。

#### 1.1 服务设计规范十条(硬性契约)

下面十条是**规定**, 不是风格建议。展开与代码依据在 §13; 现状偏离在 §13.7(★那里有几处
是**有意**偏离, 别照本节"补全"★)。

| # | 规定 | 一句话理由 |
|---|---|---|
| **R1** | **服务是 OS 的上一层**: 一个服务 = 一个(或经明示的一组)FreeRTOS 任务 + 它独占的数据。CPU 时间片**向 OS 要**(`osThreadNew`), 不自造调度。服务不跑在别人的任务里, 也不要求调用方轮询它 | 时效性由服务自己在 `run` 里的节拍保证, 不靠调用方"记得常来调我" |
| **R2** | **服务独占自己的数据**。对外只读经事件 payload 指针(§5.2 0 拷贝)或经 getter; 调用方不改服务的数据 | 谁写谁负责生命周期 —— 这是"0 拷贝"能安全的前提 |
| **R3** | **不同服务之间不得直接通信**。要协作就在 **APP 层(页面)** 汇合 —— 因为页面*就是*事件消费者 | 直连 = 隐式任务依赖 + 两条节拍耦成一条 + 组件不可删。这是 OTA 下载主循环住在页面里的原因 |
| **R4** | **对外功能 API 一般为异步**: 返回 `int8_t`, 返回值语义是**受不受理**, 不是**做没做成**。☆例外: 纯取值的 getter 与无 I/O 的状态赋值是同步的 | "做没做成"由回调/事件报, 一个返回值扛不了两个语义 |
| **R5** | **`0` 已受理 ⇒ ★恰好一次★回调; 非 0 ⇒ ★永不回调★**。所以非 0 是**终态**, 不是"等一等" | 否则调用方会等一个永远不来的事件(无看门狗时 = 静默卡死) |
| **R6** | **注入必须线程安全**: API 里只做"校验入参 + 记进服务私有的请求队列/槽 + 唤醒服务任务", 不碰 I/O、不开长临界区 | 调用方可能在任意任务里; 设备只在服务的任务里碰(§8 软件 I2C 更是不可重入) |
| **R7** | **真正的功能实现在服务的运行函数里**(`service_<svc>_run` 的 switch, 或 FatFs 那种 `osMessageQueueGet(osWaitForever)` 循环) | 这是 R1 的推论: 时间片在 `run` 里, 活也得在那儿干 |
| **R8** | **回调跑在服务的任务上下文**: 允许 `x_port_easyapp_event_send`/`osSemaphoreRelease`/`osMessageQueuePut`, 但只许"发事件 / 置标志 / 唤醒自己的任务"这类短活。★禁止 printf、禁止读写 flash★ | 你占的是服务自己的心跳(FatFs: 卷的唯一持有者; 协议: TX 任务是心跳) |
| **R9** | **回调是服务与 EasyAPP 之间的唯一桥**: 服务不认识页面、不认识事件环; 由调用方在挂回调时把"完成"翻译成**它自己的**事件 | 服务一旦 include EasyAPP 就不再可复用(宿主回归也编不动) |
| **R10** | **改服务自身的状态也要走 API**(睡眠/唤醒/开始采集): 不直接写服务内部变量, 不让别的任务代写 | 与服务自己的状态机串行化; 中断里也只能"置标志 + 让任务投队列"(§6/§7) |

> 配套的**两处签名约定**(全工程一致, 新服务照抄):
> ① 完成回调 `void (*<svc>_done_cb_t)(<句柄>, int8_t result, uint32_t done, void *p_arg)`
> —— 结果在前、`p_arg` 在最后; ② 返回码用**共用码表**(§13.3), 不用驱动层那套"每函数从 -2
> 起递增"。

### 4. EasyAPP 事件框架: 只懂三件事

事件框架代码在 `APP/EasyAPP/`(**已工作, 一般不改源码**)。写链路前必须懂它定义的
三件事, 否则事件发不出去或页面收不到。

#### 4.1 全局事件枚举(唯一改动点)

所有服务的事件 ID 都挤在**同一个**枚举里, 在
`APP/EasyAPP/inc/easyapp_page.h`:

```c
typedef enum EASYAPP_REGISTERED_EVENTS
{
    ALL_PAGES_HEAD = -1,          /* 页表区起点锚(框架用) */
    PAGE_EVENT_HEAD = 0,          /* 页面关注事件表起点(注册时首参) */
    EVT_SERVICE_ATTITUDE_NOBUSY,
    EVT_SERVICE_ATTITUDE_BUSY,
    EVT_SERVICE_ATTITUDE_DATA,
    EVT_SERVICE_ATTITUDE_NODONE,
    EVT_SERVICE_ATTITUDE_ERROR,
    PAGE_EVENT_TAIL,              /* 页面关注事件表终点(注册时末参) */
    ALL_PAGES_TAIL,               /* 页表区终点锚(框架用) */
} EASYAPP_RIGISTERED_EVENTS_t;
```

**加一个新服务的事件**: 在现有事件与 `PAGE_EVENT_TAIL` 之间插入 `EVT_SERVICE_<SVC>_*`
若干行。不要改/删已有的(数值会变, 影响历史语义)。

> 注意枚举数值=事件 ID, `ALL_PAGES_HEAD=-1`, 后面递增。加事件只做"追加到
> PAGE_EVENT_TAIL 之前", 别动头部锚的 -1/0。

#### 4.2 页对象: 每页注册一份"关注清单"

`easyapp_page.h` 定义页对象与注册宏:

```c
typedef struct easyapp_page
{
    page_event_func func;                    /* handler, int8_t (*)(void*) */
    uint32_t flag;                           /* 0=停用 1=启用(easyapp_page_enable 置 1) */
    EASYAPP_RIGISTERED_EVENTS_t page_event_lists[];   /* 关注事件表 */
} easyapp_page_t;

#define easyapp_page_register(name, fun, ...)  \
    __attribute__((used, section(".app_page_adr")))  \
    easyapp_page_t easyapp_page_##name = {    \
        .func = fun, .flag = 0,               \
        .page_event_lists = { __VA_ARGS__ } }
```

- 页对象存在**自定义段 `.app_page_adr`**, 必须与 `.app_page_head`/`.app_page_tail`
  锚点同区紧邻有序排布 → 这就是 `demo/EASYAPP.sct` 里 `EASYAPP_RAM` 段存在的唯一原因
  (§11.2)。乱放/丢散列会扫飞;
- 页面 `.c` 顶部写一次 `easyapp_page_register(REG, handler, PAGE_EVENT_HEAD,
  <关注事件...>, PAGE_EVENT_TAIL);`, 关注哪些就列哪些;
- `flag` 默认 0, **必须**在 main 里 `easyapp_page_enable(&easyapp_page_<REG>);` 才收事件。

#### 4.3 发送口与语义

`port/easyapp_port.{c,h}` 是唯一对外发送口(内部再包 `x_easyapp_event_send`):

```c
int32_t x_port_easyapp_event_send(EASYAPP_RIGISTERED_EVENTS_t event_id,
                                  uint32_t event_flags, void *event_data);
```

- **返回**: `0` 成功入 128 深静态 ring; `-1` = ring 满发送失败被丢(队列满, FIFO 丢的
  是"最新那一个", 老事件不受损——属可接受丢弃语义, 调用方不必重发);
- **event_data**: 只存指针, 框架不拷贝。**谁持有数据谁负责它的生命周期与写权限**——
  姿态链路用的是"生产者持有的最新帧 + 发它的地址"(§5.2), 页面按只读尽快读走;
- **临界区**: `OSSUPPORT=1` 时用 `osKernelLock/osKernelUnlock`(等价
  vTaskSuspendAll/xTaskResumeAll)。**只能在任务上下文调, 不能进 ISR**;
- ring 满丢弃是"生产者比消费者快"的自然背压(丢最新一个): 每周期 DATA 之后紧跟 NOBUSY,
  一旦溢出先牺牲的恰是 NOBUSY, DATA 大多保得住——真正的问题是 NOBUSY 刷得太密
  (200 事件/s) 无谓占环槽、占分发带宽, 见 §12 已知项 3。

#### 4.4 分发器 core_run

`src/easyapp_core.c` 的 `easyapp_core_run()`: 每次从 ring 取**一个**事件, 无则返回;
有则从页表头锚扫到尾锚, 对每个 `flag!=0` 且关注表命中该事件的页面调 handler。
handler 返回 `1` = 消费并停止本轮分发; 返回 `0` = 允许后续页面也收到同一事件。
页面 handler **只在 `app_core` 任务上下文被调**(见下), 不是 ISR。

### 5. 生产者服务写法(任务 + 状态机 + 控制队列 + 发布)

#### 5.1 头文件要带三样东西

`cywatch_service_<Svc>.h` 除了状态枚举和 init 声明, 还要暴露**数据帧类型**, 因为页面
要 include 它来 cast `event_data`:

```c
#include "ServiceFunction/AttitudeCalculation.h"   /* 需要样本类型时 */

/* 内部状态枚举: 只服务内部状态机用, 不是页面收的事件 */
typedef enum {
    EVT_INIT = 0, EVT_CALCULATION, EVT_SLEEP,
    EVT_WAKEUP, EVT_NODONE, EVT_ERROR,
} State_<Svc>_Service_t;

/* 一帧对外数据: 页面拿到 EVT_SERVICE_<SVC>_DATA 时把 event_data cast 成它 */
typedef struct <Xxx>_Data
{
    <sample>_t <sample>;   /* 本帧样本(单位在注释写死) */
    float <out1>;          /* 计算结果 */
    /* ... */
} <Xxx>_Data_t;

void service_<svc>_init(void);
```

#### 5.2 事件 payload = "生产者持有的最新帧"(0 拷贝)

范本(attitude)在服务 `.c` 里:

```c
static Attitude_Data_t s_latest_attitude;          /* 只本服务写 */
...
/* 每次算完: 先填最新帧, 再发它的地址(不复制) */
s_latest_attitude.attitude_sample = attitude_sample;
s_latest_attitude.roll = roll; s_latest_attitude.pitch = pitch; s_latest_attitude.yaw = yaw;
x_port_easyapp_event_send(EVT_SERVICE_ATTITUDE_DATA, 0U, (void *)&s_latest_attitude);
```

约定:

- **数据归属**: `s_latest_attitude` 归生产者, 每节拍(10ms)被覆盖; 页面拿到的指针
  "读到的总是最新一份", 但**可能比事件发出的那刻更新**(生产者在发送与页面读走之间又
  写了一次)——对"看最新姿态"够用, 对"要精确历史帧"不够(需帧序号或改成拷贝, §12);
- **0 拷贝**: 事件里只传地址。页面按只读使用、尽快算走, 不要持指针跨节拍依赖;
- **生命周期**: 数据是服务文件级 static, 永远有效, 页面不要 free、不要改所有权。

#### 5.3 状态机里发哪些事件(对照范本)

attitude 在各状态发的事件, 语义即"给 UI/上层看的当前状态补丁":

| 时机 | 发的事件 |
|---|---|
| `EVT_INIT` 进入, 开始(重试)实例化设备 | `EVT_SERVICE_ATTITUDE_BUSY` |
| 5 次实例化全失败 → `EVT_ERROR` | 交 `EVT_ERROR` 分支(见下) |
| 实例化成功, 进 `EVT_CALCULATION` | (不发, 或发 NOBUSY) |
| 每周期算出一帧成功数据 | `EVT_SERVICE_ATTITUDE_DATA` + payload=最新帧地址 |
| 每周期结束(无论成败) | `EVT_SERVICE_ATTITUDE_NOBUSY`(当前实现; §12 有密度问题) |
| `EVT_NODONE` | `EVT_SERVICE_ATTITUDE_NODONE` |
| `EVT_ERROR` | `EVT_SERVICE_ATTITUDE_BUSY` + `EVT_SERVICE_ATTITUDE_ERROR` |

#### 5.4 服务壳骨架(合并发布语义)

```c
#include "cywatch_service_<Svc>.h"
#include "ServiceFunction/<Svc>.h"
#include "../../<DEV>/adapter/cywatch_adapter_<dev>.h"
#include "cmsis_os2.h"
#include "../../APP/EasyAPP/port/easyapp_port.h"

static State_<Svc>_Service_t ServiceState;
osMessageQueueId_t <Svc>MsgQueue;                 /* 控制队列(外部改状态走这里) */
static <Xxx>_Data_t s_latest;                     /* 最新帧, 生产者独占写 */
#define SERVICE_<SVC>_LOOP_TICK  (10u)

static void service_<svc>_run(void *pvParameters)
{
    <sample>_t sample = {0};
    float out1 = 0.0f;  /* ... */
    uint32_t tick_prev = 0, tick_now = 0;
    float dt_s = 0.0f;
    int8_t ret = 0, error_cnt = 0;
    (void)pvParameters;

    while (1)
    {
        State_<Svc>_Service_t evt;
        if (osOK == osMessageQueueGet(<Svc>MsgQueue, &evt, NULL, 0))
            ServiceState = evt;                   /* 外部控制事件优先 */

        switch (ServiceState)
        {
        case EVT_INIT:
            x_port_easyapp_event_send(EVT_SERVICE_<SVC>_BUSY, 0, NULL);
            error_cnt = 0;
            while (0 != <consumer>_bsp_inst()) {  /* 内含 osDelay, 须在任务里 */
                osDelay(500);
                if (++error_cnt >= 5) { ServiceState = EVT_ERROR; break; }
            }
            if (EVT_ERROR == ServiceState) break; /* 关键: 防覆盖错误分支(§5.5) */
            <svc>_init();
            tick_prev = osKernelGetTickCount();
            ServiceState = EVT_CALCULATION;
            error_cnt = 0;
            break;

        case EVT_CALCULATION:
            ret = <consumer>_bsp_read_xxx(&sample.ax, ...);
            if (0 == ret) {
                tick_now = osKernelGetTickCount();
                dt_s = (float)(tick_now - tick_prev) * 0.001f;
                tick_prev = tick_now;
                <svc>_update(&sample, dt_s, &out1, ...);
                /* 先填最新帧, 再发地址 */
                s_latest.sample = sample;  s_latest.out1 = out1;
                x_port_easyapp_event_send(EVT_SERVICE_<SVC>_DATA, 0U, (void *)&s_latest);
            } else {
                if (++error_cnt >= 5) { ServiceState = EVT_ERROR; break; }
                tick_prev = osKernelGetTickCount();   /* 断档重基准, 防大步长 dt */
            }
            x_port_easyapp_event_send(EVT_SERVICE_<SVC>_NOBUSY, 0, NULL);
            osDelay(SERVICE_<SVC>_LOOP_TICK);
            break;

        case EVT_SLEEP:  <consumer>_bsp_hibernating(); ServiceState = EVT_NODONE; break;
        case EVT_WAKEUP: <consumer>_bsp_wakeup();      ServiceState = EVT_CALCULATION; break;

        case EVT_NODONE:
            x_port_easyapp_event_send(EVT_SERVICE_<SVC>_NODONE, 0, NULL);
            osDelay(100);                             /* 现有实现; §12 有自旋项 */
            break;

        case EVT_ERROR:
            x_port_easyapp_event_send(EVT_SERVICE_<SVC>_BUSY, 0, NULL);
            x_port_easyapp_event_send(EVT_SERVICE_<SVC>_ERROR, 0, NULL);
            osDelay(100);                             /* 现有实现无自愈, §12 */
            break;

        default: break;
        }
    }
}

void service_<svc>_init(void)
{
    ServiceState = EVT_INIT;
    <Svc>MsgQueue = osMessageQueueNew(1, sizeof(State_<Svc>_Service_t), NULL);
    if (NULL == osThreadNew(service_<svc>_run, NULL, &g_service_<svc>_attr)) {
        for (;;) { }
    }
}
```

#### 5.5 EVT_INIT 失败路径防覆盖(踩过的坑)

`while (bsp_inst)` 5 次失败会把 `ServiceState` 置成 `EVT_ERROR` 并 break 出内层循环,
**但紧接着的 `<svc>_init(); ServiceState = EVT_CALCULATION;` 会把错误分支冲掉**, 错误态
形同虚设。范本已在 while 后加 `if (EVT_ERROR == ServiceState) break;` 守卫。新服务照抄。

#### 5.6 控制队列(外部改状态)

- 外部(别的任务)想 SLEEP/WAKEUP 本服务 → `osMessageQueuePut(<Svc>MsgQueue, &evt, ...)`,
  **不直接写 ServiceState**;
- 目前 attitude 的队列尚无生产者(没有模块在投), 所以 `EVT_SLEEP/WAKEUP/NODONE`
  分支实际到不了(§12)。新服务若真需要外部控制, 把队列句柄 `extern` 或封装
  `service_<svc>_send_event(evt)` 出去;
- 中断里想改状态 → 仍走"中断置标志 + 任务投队列/发事件", 不直接在 ISR 发 EasyAPP 事件。

#### 6.1 头文件

#### 6.2 源文件

```c
#include "cywatch_app_<page>.h"
#include <stdio.h>
/* 需要解 payload 时, include 生产者服务头拿数据帧类型 */
#include "../../service/AttitudeCalculation/cywatch_service_AttitudeCalculation.h"

static int8_t page_<page>_fun(void *vparamater);

/* 关注事件表: PAGE_EVENT_HEAD ... (本页关心的 EVT_SERVICE_<SVC>_*) ... PAGE_EVENT_TAIL */
easyapp_page_register(ATTITUDECALCULATION, page_attitudecalculation_fun,
    PAGE_EVENT_HEAD,
    EVT_SERVICE_ATTITUDE_NOBUSY,
    EVT_SERVICE_ATTITUDE_BUSY,
    EVT_SERVICE_ATTITUDE_DATA,
    EVT_SERVICE_ATTITUDE_NODONE,
    EVT_SERVICE_ATTITUDE_ERROR,
    PAGE_EVENT_TAIL);

int8_t page_<page>_fun(void *vparamater)
{
    easyapp_event_t *event = (easyapp_event_t *)vparamater;
    switch (event->event_id)
    {
    case EVT_SERVICE_<SVC>_DATA:
    {
        /* event_data = 生产者最新帧地址(0 拷贝). 按只读尽快算走 */
        Attitude_Data_t *p = (Attitude_Data_t *)event->event_data;
        printf("roll=%.2f pitch=%.2f yaw=%.2f\r\n", p->roll, p->pitch, p->yaw);
        break;
    }
    /* 其它事件: 打印或驱动 UI 状态 */
    default: break;
    }
    return 0;   /* 1 = 消费并终止本轮分发; 0 = 让后续页面也能收到同一事件 */
}
```

要点:

- **注册宏必须放在文件顶层**, 生成 `easyapp_page_<REG>` 符号(在 `.app_page_adr` 段);
- handler 拿的是 `easyapp_event_t*`, 用 `event->event_id` 分支;
- 需要 payload 时按 §5.2 约定转类型、**尽快读走**(生产者每节拍覆盖);
- 返回语义: `1` 消费即停, `0` 放行给其它同事件页面; 一页一事件只有一个 handler 命中;
- **新页面建好后记得在 main.c enable + uvprojx 加组**(§11.1/§11.3), 否则收不到/没编译。

### 9. 纯算法模块 ServiceFunction 规范

与旧版一致(范本 `AttitudeCalculation`), 硬性要求:

1. **零依赖**: 只 include 标准头(stdint/stddef/math)。不 include 驱动/adapter/
   EasyAPP/cmsis/FreeRTOS/HAL; 不做 I/O、不加 osDelay;
2. **数据由调用方喂**: 定义输入结构体(如 `attitude_imu_sample_t`), 单位在头注释写死
   (加速度 g、角速度 deg/s); 量纲换算在采集侧/驱动层完成;
3. **一步一接口**: `<svc>_update(p_sample, dt_s, <out>...)` 一次调用既消耗又回填;
4. **init/reset/调参按需给**: `<svc>_init()`、`<svc>_reset()`、`<svc>_set_xxx()`;
5. **返回码**: `int8_t`, `0` 成功, `-1 p_sample null`, `-2` 起按检查顺序递增, 写进
   `@return`;
6. **文件头 `*****` 注释块**: 自述坐标系/单位/算法原理/使用流程/安装方向怎么调符号;
7. **单实例 + 非线程安全**: 文件级 static, @note 写明只能单任务上下文串行调用。

> 纯算法模块是该服务私有的(在 `service/<Svc>/ServiceFunction/`), 不全局共享。

#### 11.2 散列文件与两条链接硬约束(已踩过的坑, 必守)

散列文件 = `demo/EASYAPP.sct`, 专为 EasyAPP 页表设了高地址 RAM 段:

```
RW_IRAM1   0x20000000 0x1D000  { .ANY(+RW+ZI) }
EASYAPP_RAM 0x2001D000 0x3000  {
    *(.app_page_head, +First)
    *(.app_page_adr)
    *(.app_page_tail, +Last)
}
```

三条硬约束:

1. **`umfTarg` 必须 = 0**: uvprojx `<LDads>` 里若 `<umfTarg>1`("Use Memory Layout
   from Target Dialog"), 链接器**无视 ScatterFile**, 把页表当普通 RW 丢到 0x20000000,
   三段不紧邻 → 扫描读飞。设 `useFile=1` + `ScatterFile=..\demo\EASYAPP.sct` 之外,
   **还要把 umfTarg 归 0**;
2. **必须 `-fno-short-enums`**: AC6 默认 short-enum, 事件/哨兵会编成 1 字节, 而
   `easyapp_core_run` 按 uint32 词(4B)扫页表 → 等不到 `PAGE_EVENT_TAIL` 就扫飞。
   在 Cads MiscControls 追加 `-fno-short-enums`(add_easyapp_groups.py 已做);
3. 三条段 head(+First)/adr/tail(+Last)必须同区且顺序对, `.app_page_head`/`.app_page_tail`
   的锚对象在 `easyapp_page.c`(不动)。

**判定散列有没有真生效**: 看 map, 必须出现 `Execution Region EASYAPP_RAM (Exec base:
0x2001d000, Size: 0x2c...)`, 且 `.app_page_adr` 尺寸 = 0x24(36B=func4+flag4+7×4B 事件)。
若 `.app_page_adr` 只有 0xF → short-enum; 若页表在 0x20000000 / 无 EASYAPP_RAM 段 →
  散列被忽略。

### 13. 服务设计规范(硬性契约的展开)

§1.1 那十条是规定; 本节给出**怎么落地**、**代码依据**与**今天实现在哪里偏离**(§13.7)。
本节的两个范本是两份服务头, 它们本身就是规格书, 写新服务时**先读这两份**:

- `service/FatFs/cywatch_service_FatFs.h` —— **异步请求-回调**形态的范本(无事件、无状态机);
- `service/NordicProtocol/cywatch_service_nordicprotocol.h` —— **事件 + 异步命令**双形态的范本。

#### 13.1 服务在栈里的位置(R1)

```
        ┌ 调用方 ── APP 层(页面 / main.c) ────────────────┐
        │  调 service_<svc>_<动作>()  ── 只要返回值        │
        │  挂 <svc>_done_cb_t 回调   ── 只看回调           │
        └───────────────┬──────────────────────────────────┘
                        │ ① 异步 API(R4/R6: 校验 + 入队)
┌───────────────────────▼──────────────────────────────────┐
│ service/<Svc>/     ★一个服务 = 一个(或一组)任务 + 独占数据★ │
│   run(): 从队列取请求 / 按节拍采集 → 干活(R7)              │  ← OS 给时间片
│   ├ 数据: 服务文件级 static, 只本服务写(R2)                 │
│   ├ 请求队列 / 私有槽: API 注入的落点(R6)                   │
│   └ 出口: ② 发事件(0 拷贝 payload) 或 ③ 调回调(R8/R9)       │
└───────────────────────┬──────────────────────────────────┘
                        │ 经 <DEV>/adapter/(§8)
                    hal_driver → HAL
```

三条推论:

- **服务不知道"谁在用我"**: 出口是"事件"或"回调", 两个都不含调用方身份。所以同一个服务
  可以给 0 个消费者(§2 那条: 没页面也合法)或 N 个。
- **任务数 = 服务的"并发度声明"**: 1 个是常态。>1 时**必须写明为什么合并不了** ——
  NordicProtocol 建两个, 因为 RX/TX 是同一个状态机的两半, 而 **RX 优先级必须 > TX** 是
  协议核的硬要求, 合成一个就得放弃优先级分离 = 改协议行为。
- **服务的"忙碌"是服务自己的事实**: 是 BUSY/NOBUSY 事件(§5.3)还是查询 API
  (`service_fatfs_is_mounted()`)由消费者形态决定 —— 后者在"百 Hz 事件会挤掉
  真数据"时是对的(§13.7 #2)。

#### 13.2 服务的数据管理(R2)

按"结果给谁"选形态, 三种都算合规:

| 形态 | 何时用 | 范本 | 代价 |
|---|---|---|---|
| **① 事件 + 生产者持有最新帧**(0 拷贝) | 一对多广播, 消费者只看最新值 | Attitude / HeartRate / NordicProtocol | 读到的可能比事件那刻更新(§5.2、§12-4) |
| **② 事件 + 服务私有槽 + 槽契约** | payload 太大, 不能随帧走(4KB) | NordicProtocol 槽 0 | 寿命要写进契约、消费者要守纪律, 且**至今没有"未消费就被覆盖"的计数器** |
| **③ 完成回调 + 结果参数**(无事件) | 一对一的请求-应答 | FatFs 四个 API / NordicProtocol OTA 三件套 | 服务侧要维护"谁拥有句柄"与"在途"位 |

**什么是不合规的**: "服务写一个全局变量, app 轮询它"。FatFs 头里把这条写死了 ——
*"用事件回传文件数据等于让调用方去轮询一个全局变量, 那不是'异步', 那是'假装异步'"*。

★本工程既存的一处反例, 新代码不要照抄★: `APP/APPPAGE/DataModel/cywatch_app_datamodel.h`
是 5 个裸 `volatile` 全局(`HeartRate/Step/KCal/SpO2/FingerOn`), 没有函数 API。核实到的
实际状态是: **唯一活着的写点是 `APP/APPPAGE/HeartRatePage/cywatch_app_heartrate.c:57`
(`HeartRate = *(uint8_t *)event->event_data;`)—— 一个页面把事件 payload 抄进全局,
好让别的页面/LVGL 读**; `Step`/`KCal` 全树**没有写者**, `SpO2`/`FingerOn` 的写点在
`cywatch_app_spo2_page.c:195-196` 是**注释掉的**。⇒ 读侧拿到的是恒 0。这是"页面之间用
全局量通信"的形态, 与 R3 的精神相悖(该走事件); 头文件自己也写明 *"volatile 不能替代
互斥"*、4 字节量可能被撕裂。**它不是范本, 是遗留**。

#### 13.3 异步 API 契约(R4/R5/R6/R7)

**三段式**(API 里只做前两段):

```c
int8_t service_<svc>_<动作>(<入参...>, <svc>_done_cb_t pf_done, void *p_arg)
{
    /* ① 校验: 服务是否起来了 / 入参非空 / 句柄合法 / 所有权 / 在途位 */
    /* ② 注入: 组一个请求记录, 投进服务私有队列, 唤醒服务任务 */
    return 0;   /* 或是下面码表里的负值 —— 两者都是终态, 见 R5 */
}
```

**统一的返回码表**(照 FatFs 那张; 服务层**有意**不用驱动层"每函数从 -2 起递增"那套,
理由见 §13.7 #6):

| 码 | 含义 | 有回调吗 |
|---|---|---|
| `0` | 已受理 | ★恰好一次★ |
| `-1` | 服务未初始化; 或链路忙(adapter 原样透传) | 无 |
| `-2` | 入参为空/非法(含 `pf_done == NULL`) | 无 |
| `-3` | 参数超范围(仅当 API 自己不做长度校验时才有这条路) | 无 |
| `-4` | 句柄不在池中 / 上一条命令还在途 —— ★是"现在别发", 不是错误★ | 无(但**上一条**的回调会来) |
| `-5` | 所有权不符(提交者不是句柄持有者) | 无 |
| `-6` | 该句柄上已有一条在途请求 | 无 |
| `-7` | **队列满 —— 未受理** | ★无★ |

两条**写文档**的纪律:

- 每个函数的 `@return` **只列它真能返回的子集**, 并且把"不可能出现的码"**明写出来**
  —— NordicProtocol 头就写了一句 *"★`-3` 不可能出现★: 长度由本 API 自己定…写在这里免得
  读者去找它"*。防的是后人花时间去追一条不存在的路径。
- 每个函数都要有一句 **`@note ★返回值必须看★`**, 并说清不看会怎样。例:
  `service_fatfs_init` 的 -1/-2 *"只可能是内核堆不足, 而 `configUSE_MALLOC_FAILED_HOOK`
  与 `configASSERT` 都是关的, 不看不报 —— 表现是'文件 API 全部返回 -1', 串口上一个字都不会有"*。

**入参寿命: 两种语义, 必须在头里写死**★最容易搬错纪律的地方★

| 语义 | 含义 | 范本 | 后果 |
|---|---|---|---|
| **借用** | `p_path`/`p_buf` **借到回调返回那一刻** | FatFs(`service_f_write` 直接在调用方缓冲上 `f_write`, **不拷贝**) | `char path[32]; sprintf(...); service_f_open(path, ...);` **出门就悬空** —— 要传栈上字符串就必须等回调 |
| **入缓冲即拷贝** | 返回后调用方缓冲可复用 | NordicProtocol(`service_nordicprotocol_send` 入环即拷贝) | 传栈上临时数组没问题 |

★两个头里都写了"别把另一种的纪律搬过来"★ —— 这不是理论风险, 是两种实现真的不同。

**链式调用(在回调里接着调本服务的下一个 API)是合法的**, 但**必须由服务明说**"回调之前
状态已复位", 否则会自己判自己违规:

- FatFs: 所有权沿回调链继承(`.c` 的 `s_cb_owner`), 否则"open 的回调里接着 post write"
  会被自己的所有权检查判 `-5`;
- NordicProtocol: 驱动在调回调**之前**已把 TX 状态全部复位、`s_msg_busy` 清零, 所以从回调
  里接着发不会撞 `-1`。头里点名这是"下载主循环自定节奏"所依赖的性质。

⚠ 但**同一时刻只允许一条命令在途**的 API(OTA 三件套)是例外: 每放行一块要发两条
(`0x04` + `BLKREQ(N+1)`), 两条之间**必须**隔着一次完成回调再发第二条, 连着调必拿 `-4`。

#### 13.4 回调契约(R8/R9)

- **上下文**: 服务的任务。写进头里(FatFs:*"在 FatFs 任务上下文里被调"*;
  NordicProtocol:*"在 **TX 任务上下文**被调"*)。⇒ 因为 CMSIS 的规则, 这**恰好**是
  `x_port_easyapp_event_send` 需要的上下文(它只能在任务里调, 不能进 ISR)。
- **只许短活**: 发事件 / 置标志 / 唤醒自己的任务。**禁止 printf**(阻塞式 polled,
  一行 ≈ 5.2ms)、**禁止读写 flash**(一次页写 ≈ 79ms)。理由不是"优雅", 是**你占的是服务
  自己的心跳**: FatFs 回调跑在*卷的唯一持有者*上; 协议回调跑在 TX 任务上。
- **签名统一**: `void (*<svc>_done_cb_t)(<句柄>, int8_t result, uint32_t done, void *p_arg)`
  —— **结果在前、`p_arg` 在最后**。NordicProtocol 头明写"形态对齐 `fatfs_done_cb_t`,
  让读过那份的人不必重学一遍"。
- **结果码用符号位分工**(范本 FatFs, 值得抄): `result > 0` = 下层库的码**原样透传**
  (`FRESULT` 是 1..19); `result < 0` = 服务自己的码(-1 卷未挂载 / -2 内部状态异常)。
  好处是**不需要二次映射表**, 也不会把 `FR_DISK_ERR(1)` 和"未挂载"混成一个码。
- ★**结果不要存进服务/页面的 static 再让回调去读**★ —— 用 `p_arg` 带上下文(或让 `p_arg`
  指向调用方自己的结构)。这是"回调恰好一次"的自然推论。
  (页面那侧今天有一处弱形态: OTA 页用 `s_store_result`/`s_store_done` 静态量 + 用
  `event_flags` 带 op 号把回调结果转成事件。它能工作, 但**多了一次"页面静态量"这个
  中转**; 新服务优先用 `p_arg`。)
- **服务不认识 EasyAPP**(R9): 今天**没有任何服务发事件** —— 结果一律走调用方回调
  (FatFs 是范本)。要发事件必须由**服务壳的 sink 回调**转译, 服务本身仍然不 include
  EasyAPP 的头、不调它的 API。**两种形态都合规**, 分界是"结果给一对多还是给一对一"。

#### 13.5 服务之间不得直接通信(R3)

**禁止**: include 另一个服务的头 / 调它的 `service_<svc>_*()` / 读它的 static /
把另一个服务的 `event_data` 指针直接转手。

> **现状核实(2026-09-22)**: 全部 `service/*/cywatch_service_*.c` 里**没有一处**服务
> include 另一个服务的头或调用它的 API。⇒ 这条规定**与今天的代码一致**, 是"把已经在做的
> 事写成规定", 不是"要求改现状"。

**为什么**:

1. **直连 = 隐式任务依赖**。服务的时效性由它自己在 `run` 里的节拍保证(§5.4 的
   `osDelay(SERVICE_<SVC>_LOOP_TICK)`); 一旦 A 直接调 B 的 API, A 的节拍里就嵌了 B 的
   队列深度与阻塞行为 —— 两条节拍耦成一条, 而**耦合点不在任何一个服务里**(它在调用点),
   读代码时看不见。
2. **直连绕过了"谁做编排"这个可读性问题**。事件链的强项是"生产者不知道消费者"; 直连把
   依赖方向钉死在代码里, 加第三个消费者就要改生产者。
3. **可删性**。本工程反复用过这个性质: 删掉 `APP/APPPAGE/NordicProtocolPage` **没有动任何
   服务**(它只是零个消费者了); 裁剪存储链只动了 uvprojx 清单与 `main.c` 的调用点。
   服务互连会把这个性质毁掉。

**那协作怎么做? 由 APP 层(页面)编排** —— 页面*就是*事件消费者, 多路结果在它这里汇合。

- **落地例(用户拍板, 本工程最重要的一条形态决定)**: OTA 下载主循环住在
  `APP/APPPAGE/UserPage/cywatch_app_ota_page.c`, 把三路汇在一起 ——
  NordicProtocol 的 `EVT_SERVICE_NORDIC_MESSAGE` / `EVT_SERVICE_OTA_CMD_DONE`、
  FatFs 的完成回调(页面在 `pf_done` 里发 `EVT_SERVICE_OTA_STORE_DONE`)、
  LVGL 的投值 API(`watch_page_ota_post_*`)。**不建 `service/OtaDownload/`**。
- ★这条与 `doc/固件下载流程.txt` §3.3 **故意相反**★(那份文档设想"建任务 + 私有回复队列",
  理由是"任务收不到 EasyAPP 事件")—— 而**页面收得到**, 所以"FatFs 完成发事件"才是自然
  机制, `fatfs_req_t` 也不需要 `reply_q`。**别照那份文档"修好"它**。
- **反向判据**: 如果是**服务**需要另一个服务的能力(而不是它恰好被编排), 那说明层次划错了
  —— 该把它们合成一个服务, 或把公共能力**下沉**到 `<DEV>/hal_driver/` 或 `system/`。别用
  服务互连当"分层"。
- **唯一允许的跨服务形态**: `app → 服务` 的**查询 API**(`service_fatfs_is_mounted()`、
  `service_fatfs_size()`)。那是"取事实", 不是"驱动对方干活"。

#### 13.6 服务改自身状态, 也要走 API(R10)

用户的传感器例子(睡眠/唤醒/采集)落到本工程的形态:

| 形态 | 什么时候 | 写法 |
|---|---|---|
| **异步**(动作有耗时/要碰设备) | 最常规 | `service_<svc>_set_state(...)` → 投控制队列 → 返回 `0`/非 0, 结果发事件 |
| **同步**(纯赋值, 无 I/O) | 只是改个阈值/标志 | 可以直返 `0/-1`, 但**必须在头里写明只允许在哪个上下文调** |

**控制队列的正确写法**是 §5.6 + §5.4: `osMessageQueueNew(1, sizeof(State_<Svc>_Service_t), NULL)`,
在 `run` 的**顶部**用 `osMessageQueueGet(..., 0)` 抢占式读取(外部控制优先于本周期的工作)。

**注入的口子**: 封装 `service_<svc>_send_event(State_<Svc>_Service_t evt)`, **而不是**把
`<Svc>MsgQueue` 句柄 `extern` 出去 —— 后者等于把服务的内部结构公开(违反 R2 的精神)。

**中断里想改状态**: 置标志 + 让任务投队列。**绝不**在 ISR 里投队列或发 EasyAPP 事件(§6/§7)。

⚠ **现状**: attitude 与 heartrate **都建了控制队列, 但至今没有生产者** ⇒ 它们的
`EVT_SLEEP/EVT_WAKEUP/EVT_NODONE` 分支**实际到不了**(§12 已知项 5)。也就是说
"app 可以改传感器的状态"这条规定**在本工程还没有一个活着的例子** —— 谁先做谁补那个
`service_<svc>_send_event()` 封装。

#### 13.7 现状偏离表(逐条知道; ★标"有意"的别照本节"补全"★)

| # | 服务 | 偏在哪 | 性质 |
|---|---|---|---|
| 1 | **FatFs** | 不发任何 EasyAPP 事件、没有控制队列/状态机、**不加自己的互斥量** | ★**有意**, 头里逐条写了理由★: 任务收不到事件(只有注册页面收得到), 所以"事件回传文件数据"= 让调用方轮询全局变量; 状态只有"卷挂上没有"这一个**事实**不是事件流; `FF_FS_REENTRANT == 1` 已让 `ff.c` 每次 API 进出取/放卷互斥量, 再加一把只是多出"锁序"这个失败面 |
| 2 | **NordicProtocol** | **两个任务**而非一个; **不发 BUSY/NOBUSY** | ★**有意**★: RX 优先级必须 > TX 是协议核硬要求; 每帧发一对 BUSY/NOBUSY 会以百 Hz 量级占据 128 深事件环, 把真有数据的 DATA/MESSAGE 挤掉 |
| 3 | **NordicProtocol / OTA 封装** | **不打重试** | ★**有意**(用户拍板)★, 与 `doc/固件下载流程.txt` §2.4 故意不一致: 那条是给"将来的 OtaDownload 任务"写的, 而本工程没有那个任务; 替代品是"回调本身就是'发下一条'的时机" |
| 4 | **Lvgl** | `init` 之外不导出功能 API, 也**不发事件**; 投值入口在**页面侧**(`LVGL/port/lv_watch_page_ota.h` 的 `watch_page_ota_post_*`) | 形态是"被投值", 不是"发布者"。**合规**: 它属于 §13.2 形态③ 的变体(一对一 + 调用方自取), 且严格遵守"只有 lvgl 任务能调 `lv_*`" |
| 5 | **Attitude / HeartRate** | 控制队列有句柄、**无生产者** ⇒ 状态类 API 实际不可达; HeartRate 的页面还把事件 payload 抄进 **DataModel 裸全局** | **既存欠账**, 见 §13.2 末段与 §12-5 |
| 6 | **FatFs / 全体服务** | 返回码**不是**"每函数从 -2 起按出现顺序递增"(那是 `cywatch-bsp-driver` 给**驱动层**的规矩), 而是**共用一张码表** | ★**有意**, 头里写明理由★: "四个函数是同一张对外 API 面, 共用一张码表调用方才能一处判断" |
| 7 | **全体** | 没有统一的"未初始化"形态: `service_fatfs_init` 返 `int8_t`, `service_heartrate_init` 是 `void` | **建议新服务一律 `int8_t` + 码表**(§12 已有同向建议), 否则"内核堆不足"这类失败无处报 |

#### 13.8 写一个新服务的检查单

1. 目录/文件/命名照 §3.1; 事件枚举追加到 `PAGE_EVENT_TAIL` 之前(§4.1);
2. **写下"服务↔调用方的接口"再写实现**: 每个 API 的 `@return` 码表(只列真能返回的)、
   入参寿命(借用 or 拷贝)、回调的上下文与禁止事项(R8)、回调签名(R4/R8);
3. 想清 §13.2 选哪种数据形态, 并在头里写明**为什么**;
4. 设备只经 `<DEV>/adapter/`(§8); 例化放任务内 `EVT_INIT`(含 `osDelay`);
5. 依赖 EasyAPP **只在服务壳的出口那一层**(发事件 / 或压根不发); 服务不 include 页面;
6. 不给别的服务留 include 口(R3); 需要协作就把编排写在页面里;
7. 状态类 API 用控制队列 + `service_<svc>_send_event()` 封装(§13.6);
8. 接线: uvprojx 组 + IncludePath + `main.c` 的 init(§11.1/§11.3, ★只许跑
   `add_lvgl_service_groups.py` / `add_nordic_service_groups.py` /
   `add_fatfs_service_groups.py` 三个脚本★);
9. 报告结果时引用 `demo/proto_regress/README.md` §4/§4.1/§4.3 —— **不许写"已验证可跑"**。
